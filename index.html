설계할 때는 확장성이나 안정성만을 무조건 추구하기보다, 현재의 요구사항과 앞으로의 변화 가능성을 함께 고려해 필요한 수준의 구조를 선택합니다. 지금의 복잡도를 불필요하게 키우지 않으면서도, 변화가 필요한 시점에 수정하고 확장할 수 있도록 트레이드오프를 판단해 설계해 왔습니다.

USE

개발자에게 좋은 구조보다 실제로 사용하는 사람이 실수 없이 사용할 수 있는 구조를 고민합니다. 반복되는 작업이나 사람이 실수하기 쉬운 지점을 발견하면 검증과 자동화로 줄이고, 필요한 경우 직접 사용할 수 있는 도구로 만듭니다.

TRACE

추적할 수 있는가

정상적인 흐름만 설계하지 않습니다. 데이터와 요청의 흐름을 추적할 수 있어야 문제가 발생했을 때 원인을 찾고 영향을 확인할 수 있다고 생각합니다.

RECOVER

복구할 수 있는가

모든 오류를 예방할 수는 없다고 생각합니다. 대신 문제가 발생했을 때 안전하게 복구할 수 있는 경로를 설계합니다. 자동화할 수 있는 부분은 시스템이 처리하고, 사람이 판단해야 하는 지점은 로그와 복구 기능을 통해 개입할 수 있도록 합니다.

CASE 01

외부 주문 연동과 장애 복구를 고려한 시스템 설계

엘에스컴퍼니 · 관광 레저 플랫폼14개월 설계·개발5년+ 라이브 운영MariaDB · MSSQL(레거시)성수기 일 5만 건 주문
문제
  • 네이버·쿠팡 등 외부 채널 주문 API를 서비스 서버가 직접 처리해, 서비스가 죽으면 주문 수집도 함께 중단
  • 장애 시간대의 API 요청/응답이 남지 않아 누락 여부를 확인할 근거가 없음
  • 채널·내부 데이터 불일치, 상품 연결 휴먼에러까지 모두 개발자가 직접 확인하고 재처리
판단

외부 채널과의 통신은 서비스 서버의 생존 여부와 분리되어야 한다. 그리고 장애 이후의 불일치는 자동화만으로 풀지 않고, 역할별 복구 경로로 푼다.

설계

①API 서버 분리 — 장애 격리

외부 채널 연동을 독립 서버로 옮겨, 서비스 서버가 다운되어도 주문을 계속 받고 로그로 남깁니다.

②원천 데이터 보존 — 구간 추적

요청/응답과 처리 로그를 API 서버가 따로 관리해, 장애 시각 기준으로 누락 여부를 확인할 수 있습니다.

③운영자 재처리 — 비개발자 복구

원천 데이터는 서비스 서버가 아니라 API 서버에 있으므로, 운영자 화면이 내부 API로 API 서버를 호출해 상품 연결 수정·개별 주문 재처리·불일치 보정을 직접 처리합니다.

④개발자 일괄 재처리 — 구간 복구

장애 시각 기준 일괄 재처리 API를 두되, 전용 토큰 인증으로 일반 사용자의 접근을 막았습니다.

결과
  • 서비스 장애와 외부 수집 장애를 분리해 장애 전파 범위 축소
  • 외부 장부·업체 지원 없이 내부 데이터와 자체 도구만으로 원인 확인·복구
  • 개발자가 필요한 장애와 운영자가 처리할 예외를 분리
  • 수집 → 저장 → 서비스 반영 → 복구를 하나의 운영 흐름으로 설계
CASE 02

판매와 관광지 정산을 분리한 가변 상품 데이터 모델

엘에스컴퍼니 · 관광 레저 플랫폼상품 데이터 모델 재설계MariaDB일 5만~10만+ 사용 처리
문제
  • 판매상품과 관광지 정산 기준을 하나의 상품 구조로 표현
  • 판매채널은 결제금액 기준, 관광지는 1회 입장·사용 횟수·회원 활성화 등 이용 기준으로 정산
  • 패키지(여러 관광지 중 일부 이용), 1회권·회차권·연간권마다 방식이 달라 유형 추가 시 테이블과 로직을 함께 수정
판단

“고객이 무엇을 얼마에 샀는가”와 “관광지에 얼마를 정산하는가”는 같은 기준으로 계산되지 않는다. 그러니 같은 개념이 아니다.

설계

판매가가 바뀌어도 관광지 정산 기준은 흔들리지 않고, 관광지의 이용·정산 기준이 바뀌어도 판매상품 구조는 그대로입니다. 새 상품 유형은 테이블 수정이 아니라 관계·조건 데이터 추가로 표현됩니다.

결과
  • 설계 결함으로 인한 치명적 정산 사고 0건
  • 퇴사까지 약 4년간 핵심 정산 구조 변경 없이 운영, 현재 5년+
  • 판매상품 · 가격/채널 · 관광지 상품 · 관계 · 이용 조건으로 책임 분리
  • 하나의 판매상품을 여러 관광지 상품에 연결하는 패키지 표현
  • 상품 속성과 조합을 코드가 아닌 데이터로 표현
  • 판매가격 변경과 정산 기준 변경의 상호 결합도 제거
CASE 03

공통 API와 표준 검증 프로세스로 외부 연동 표준화

엘에스컴퍼니 · 관광 레저 플랫폼공통 API · QA 도구 구축API 명세 직접 문서화
문제
  • 소규모 제휴사·신규 영업 업체는 연동할 API 자체가 없는 경우가 많음
  • 한정된 개발 리소스로 제휴처마다 API를 새로 설계하는 방식은 지속 불가
  • QA 인력 없이 신규 연동마다 정상·오류 요청을 개발자가 직접 반복 테스트
판단

제휴처마다 API를 만들지 않는다. 판매처용과 사용처용 공통 API를 하나씩 정하고, 제휴처가 그 규격에 맞춘다. 검증 방식은 호출 방향이 결정한다.

설계
자동화 QA · 요청 없이 직접 만든 도구
  1. 1테스트 케이스 선택
  2. 2API 요청
  3. 3정상/오류 응답 확인
  4. 4오류별 대응 방법 확인

의도적으로 오류 상황을 만들어 응답과 채널 측 대응 방법을 함께 보여주도록 구성해, 신규 연동마다 개발자가 요청을 조립하던 반복을 없앴습니다.

결과
  • 제휴처별 개별 API 개발 → 판매처용·사용처용 공통 API 2종 기반 연동으로 전환
  • 규격 → 연동 → 검증 → 오류 대응까지 반복 업무 축소
  • 반복 테스트에 쓰던 개발 시간을 신규 연동·시스템 개발로 전환
  • 공통 API 명세와 연동 방법 직접 문서화

CASE 05

서버 0에서 3개 시스템 구축 — 데이터 · 통계 · AI 영역의 독립 설계

LKF파트너스 · 배달 플랫폼 통합 관리 SaaS백엔드 · 백오피스 · 수집/통계PostgreSQL · ClickHouse
통계 서버 물리 분리

주문·리뷰는 조회로 끝나지 않고 통계와 그래프로 계속 집계될 데이터다. 서비스 DB에서 수집과 집계를 같이 돌리면, 규모가 커질수록 서비스가 먼저 느려진다.

스키마 분할 설계 · 서버는 하나, 경계는 미리

작은 서비스에서 시작하기 때문에 처음부터 서버를 나누지 않았다. 대신 추후 확장을 고려해 공통 · 백오피스 · 서비스를 스키마 단위로 분할 설계했다.

공통코드문자열 대신 PK 참조

플랫폼·상태·상품 유형을 공통코드 PK로 참조하고, 외부 API 값은 extra_value로 관리해 외부 값이 바뀌어도 업무 테이블은 수정하지 않습니다.

관리 규칙구조만 보고 추적 가능하게

테이블 코멘트와 정의서에 참조하는 코드 그룹 PK를 명시하는 원칙을 세워, DB를 열어보지 않아도 연결 관계를 알 수 있게 했습니다.

AI 모델 교체 가능한 구조
결과
  • 대용량 수집·통계를 서비스와 물리적으로 분리해 서비스 영향 최소화
  • ClickHouse 기반 OLAP 환경으로 향후 집계·그래프 요구 대비
  • 서버 하나로 작게 시작하되, 스키마 분할로 확장 시 서버 분리 경로 확보
  • 공통코드 기반 모델로 플랫폼·상태·유형 하드코딩 최소화
  • 테이블 정의·관리 규칙까지 표준화
  • AI 모델·프롬프트의 코드 의존도를 낮춰 교체·설정 변경에 대응
CASE 06

AI 기반 개발 프로세스(Dev-Flow) 설계

LKF파트너스AI 협업 프로세스 재설계Jira · Confluence · MCP
문제 · 바이브코딩이 남긴 기술 부채
  • 플랫폼 주문·리뷰 수집 시 중복 검증 없이 기존 데이터를 삭제 후 재입력
  • 서로 다른 기능의 데이터를 한 테이블에서 관리해 설정 변경이 다른 기능에 영향
  • 연결 테이블 없이 분리된 테이블 — 체인 구조 확장 시 참조 무결성 붕괴 위험
  • 공통화되지 않은 쿼리로 기능 하나에서 최대 16개 쿼리가 개별 실행
판단

A부터 Z까지 사람이 문서화하면 AI를 써도 일이 줄지 않고, 설계까지 AI에게 맡기면 정합성을 보장할 수 없다. AI를 막는 대신, 사람과 AI가 잘하는 영역을 나눈다.

설계

1설계는 사람이

테이블 관계, 데이터 흐름, 비즈니스 규칙은 사람이 결정해 AI가 구조를 임의로 바꾸거나 요구사항을 추측하는 범위를 제한합니다.

2Jira 기반 계약 검수

API별 요청·응답과 사용 쿼리를 이슈에 남기게 하고, 설계 흐름 일치·반복 쿼리·정합성 위험을 확인합니다.

3Confluence를 SSOT로

로컬 Redmine에 흩어진 개인 문서를 걷어내고, 작성 규칙과 예시를 Confluence에 표준화해 MCP로 AI와 사람이 같은 기준을 봅니다.

4비용 에이전트 이중 검증

과도한 쿼리 호출이라는 기존 부채가 재발하지 않도록, 구조적으로 필요한 처리인지 사람이 최종 판단합니다.

결과
  • 바이브코딩으로 쌓인 정합성·DB 비용 부채 직접 개선
  • 데이터 설계와 구현의 책임을 분리해 AI 활용 범위 정의
  • AI 구현 결과에 대한 사람의 핵심 검수 체계 구축
  • AI를 코드 생성기가 아닌 구현·검증의 협업 주체로 정립
CASE 07

정산 수동 등록 자동화 및 복구 기능

LKF Partners · Internal Admin Tool주 1회 · 정산 테이블 5종 개발자 수동 등록자체 발굴 개선

주간 단위로 반복되는 정산 데이터 등록 과정에서 발생하는 수동 DB 작업과 휴먼에러 가능성을 줄이기 위해 관리자 웹 기능을 직접 설계·구현했습니다.

기존에는 5개의 정산 기준별 데이터를 DB 관리 도구를 통해 개발자가 직접 테이블을 선택하고 수동으로 등록했습니다. 테이블을 잘못 선택하거나 파일 구조가 맞지 않을 경우 오류가 발생할 가능성이 있었으며, 등록 이후 문제가 발생하면 해당 기간 데이터를 삭제한 뒤 다시 등록하는 방식으로 복구했습니다.

문제
  • 정산 기준별 5개 테이블에 각각 데이터를 직접 등록하는 반복 업무
  • 파일과 테이블을 잘못 매칭할 경우 등록 오류 발생 가능
  • 컬럼명을 완전히 동일하게 비교하는 방식은 작은 차이에도 등록을 막아 사용자 부담 증가
  • 테이블별 데이터 타입만으로는 충분한 구분이 어려움
  • 주간 정산 기간이 휴일 등에 따라 달라질 수 있어 고정된 날짜 규칙만으로 처리하기 어려움
설계

파일명과 테이블명의 일치 여부를 기본 선택 규칙으로 사용하되, 파일명이 다르면 자동 선택하지 않고 사용자가 직접 테이블을 선택할 수 있도록 구성했습니다. 파일 테이블별 컬럼 수로 기본 구조를 검증하고, 각 셀의 빈 값 여부와 숫자형 컬럼의 숫자 입력 여부를 확인합니다.

업로드 로그 테이블을 별도로 두어 등록 이력을 확인할 수 있게 하고, 특정 정산 기간을 선택해 해당 기간의 데이터를 초기화한 뒤 다시 등록할 수 있는 복구 기능을 구현했습니다. 복구 후에는 재등록이 필요하다는 안내를 관리자 화면에서 제공합니다.

검증 기준을 고른 과정

✕ 제외컬럼명 완전 일치 비교

작은 차이에도 등록을 막아 사용자 부담이 커집니다.

✕ 제외데이터 타입 비교

테이블별 데이터 타입만으로는 충분히 구분되지 않습니다.

✓ 채택테이블별 컬럼 수

테이블마다 컬럼 수가 달라 기본 구조 검증의 공통 기준으로 사용했습니다.

+ 보완셀 단위 검증

빈 값 여부와 숫자형 컬럼의 숫자 입력 여부를 확인합니다. 실제 데이터 특성과 사용자 경험을 고려해, 등록 가능한 범위에서 오류를 사전에 검출합니다.

기간 초기화 · 시작일은 고르고 길이는 고정
결과
  • 직접 등록 + 테이블 확인 약 20분 → 약 1~5분
  • 반복적인 DB 직접 작업을 관리자 화면으로 전환
  • 등록 과정의 휴먼에러 가능성 감소
  • 개발자가 하던 등록·복구 업무를 비개발자 담당자도 처리할 수 있도록 자발적으로 구현

이 기능은 별도의 요구사항으로 전달받아 구현한 것이 아니라, 반복적으로 수행하던 업무 과정에서 직접 비효율과 오류 가능성을 발견하고 업무를 단순화하기 위해 설계·구현한 개선 작업입니다.
