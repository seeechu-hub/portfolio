CASE 01

배달 플랫폼 통합 관리 SaaS

LKF파트너스 · 팀장2025.10 – 2026.090-to-1 설계NestJS · Next.jsPostgreSQL · ClickHouseAWS
요구사항

배달 플랫폼의 주문·리뷰 데이터를 수집해 통계와 AI 기능으로 활용하는 통합 관리 SaaS를 설계·구축했습니다.

  • 여러 배달 플랫폼의 주문·리뷰 데이터를 외부 API로 수집
  • 수집한 데이터를 바탕으로 여러 가지 통계 데이터를 빠른 속도로 제공
  • 수집한 데이터를 기반으로 AI 기능 제공 (CASE 03 리뷰 AI 자동 답변에서 상세)
판단
  • 엘에스컴퍼니에서 검증한 장애 전파 차단 구조를 배달 플랫폼 주문·리뷰 수집에도 적용해야 한다고 판단
  • 통계 서버의 데이터베이스는 대용량 통계 처리에 유리한 DB로 결정해야 한다고 판단
  • 유저 수를 예측할 수 없는 작은 규모로 시작하므로, 이후 확장 시 쉽게 분리할 수 있도록 구조를 설계해야 한다고 판단
  • 비동기 처리는 Redis 같은 별도 큐를 도입하면 서버·컨테이너를 추가로 운영해야 하는데, 팀 내 운영 경험이 없고 일정도 촉박하며 2인 개발팀이 운영해야 해, 엘에스컴퍼니에서 운영해 본 DB 테이블 큐와 스케줄러 구조를 적용하는 것이 적절하다고 판단. 작업 상태가 DB에 남아 관리자 화면에서 바로 확인하고 후속 처리할 수 있는 점도 고려
  • 외부 플랫폼 코드처럼 바뀔 수 있는 값이 여러 기능에서 반복되므로, 값 변경이 업무 데이터에 영향을 주지 않는 구조가 필요하다고 판단
  • 엘에스컴퍼니에서의 운영 경험을 바탕으로, 로그와 요청 추적이 가능한 구조를 처음부터 설계해야 한다고 판단
설계

1통계 서버 물리적 분리 (ClickHouse)

AI로 빅데이터용 통계 DB 후보를 제안받아 통계 요구사항 기준으로 검토했고, 두 가지 이유로 ClickHouse를 채택했습니다.

  • 배달 플랫폼 주문·리뷰 데이터는 짧은 시간만 상태가 바뀌고 이후 고정되어, 적재·집계 위주인 ClickHouse에 적합
  • Materialized View가 적재 시점에 집계를 함께 갱신해, 통계 전용 데이터 처리를 따로 만들 필요가 없음

통계 서버가 저장·정합성 관리·집계를 전담하고, 서비스 서버에는 필요한 통계만 API로 제공합니다. 수집은 별도 워커 서버의 DB 테이블 큐와 Batch Scheduler가 정해진 시간에 유저별로 처리합니다. 실패 건은 관리자가, 특정 기간 전체 실패는 개발자가 기간을 지정해 재처리하도록 설계했고, 큐 처리를 워커 서버로 분리해 규모가 커지면 Redis 등 별도 큐로 전환할 수 있게 했습니다.

2공통 · 백오피스 · 서비스 스키마 분리

현재 규모에서는 단일 DB로 운영하되, 향후 서비스가 독립적인 시스템으로 분리될 가능성을 고려해 공통·백오피스·서비스 영역을 스키마 레벨에서 분리했습니다.

3공통코드 구조와 테이블 관리 기준

플랫폼명·리뷰 상태·상품 유형처럼 반복되는 값은 공통코드로 관리하고, 업무 테이블은 문자열 대신 공통코드 PK를 참조하도록 했습니다. 외부 API용 값은 extra_value로 따로 두어, 쿠팡 코드가 coupang에서 다른 값으로 바뀌어도 코드 정의만 수정하면 됩니다.

그룹코드는 영문 대문자 2~4자리로 제한하고, 테이블 정의서에 공통코드 연관 관계를 명시하는 것을 원칙으로 정했습니다.

4공통 API 통신 함수와 운영 공통 기능

공통 개발 규칙과 API 통신 규칙을 정의하고, 모든 API 통신이 반드시 거치는 공통 함수를 개발해 미들웨어에서 자동으로 호출되도록 적용했습니다. 이 공통 처리에서 API 요청마다 고유 ID를 발급하고 민감정보를 마스킹해 AWS CloudWatch에 기록하며, 인증과 IP Rate Limit을 함께 처리하도록 구성했습니다.

결과
  • 외부 API 수집과 대용량 집계를 워커·통계 서버로 분리해, 외부 연동 장애와 집계 부하가 서비스로 전파되지 않는 구조 구축
  • ClickHouse Materialized View로 별도 통계 처리 없이 미리 집계해, 조회 시 재계산 없이 바로 응답하는 통계 조회 구조 구축
  • 작은 규모에 맞게 단일 DB와 DB 큐로 운영하면서, 스키마 분리와 워커 서버 분리로 규모 확장 시 DB 분리·별도 큐 전환이 가능한 경계 확보
  • 공통코드로 플랫폼·상태·상품 유형 하드코딩을 최소화하고, 테이블 정의·관리 규칙까지 표준화
  • 모든 API 통신에 공통 처리를 자동 적용해, 요청 ID 기반 장애 추적과 개인정보 마스킹 체계를 팀 전체에 일관되게 적용
CASE 02

Claude Code Skills 기반 개발 업무 프로세스 설계 및 적용

LKF파트너스 · 팀장2026.04 – 2026.05자발적 개선Claude Code Skills · Plan ModeJira · Confluence · Atlassian MCP
문제

AI 활용으로 개발 속도는 빨라졌지만, 팀 단위 개발 과정에서 다음과 같은 문제가 발생했습니다.

  • AI가 주문·리뷰 수집 로직을 중복 검증 없이 기존 데이터를 삭제 후 재입력하는 방식으로 구현
  • 기능 구현을 지시하면 AI가 필요한 테이블을 제안하는 대신 임의로 생성해, 테이블 간 연결 구조가 없어 참조 무결성 저하 가능성 존재
  • 공통화되지 않은 쿼리가 반복 호출되어 단일 기능 실행 시 최대 16개의 DB 쿼리가 발생하고, DB 부하 및 비용 증가 가능성 존재
  • 구현 완료 후 설계 검토 내용, 판단 근거, 구현 이유 등이 충분히 공유되지 않아 담당자 변경 시 기존 설계를 다시 파악해야 하는 문제 발생
  • 개발자별 연차와 AI 활용 방식의 차이로 AI가 설계 의도와 다르게 구현하는 경우가 발생하고, 추가 수정 및 검토에 필요한 개발 시간 증가

이를 해결하기 위해 사람의 설계와 판단은 유지하면서 AI의 구현 및 검수 활용을 표준화하는 개발 프로세스를 구축했습니다.

판단

기존에는 사람이 요구사항부터 데이터 구조, 처리 흐름까지 A부터 Z까지 문서화한 후 AI에게 구현을 요청했습니다. 이 방식은 설계 통제력은 높지만 문서와 반복 작업이 많아 생산성 향상이 제한적이었습니다. 반대로 데이터 모델과 흐름까지 AI에게 맡기면 구현 속도는 높아지지만, 비즈니스 규칙과 데이터 정합성을 AI가 정확하게 판단한다고 보장하기 어려웠습니다.

AI 활용을 제한하기보다 팀의 설계 기준과 판단 과정을 AI가 일관되게 참조할 수 있도록 개발 프로세스를 표준화했습니다. 사람은 데이터 구조·데이터 흐름·핵심 설계를 판단하고, AI는 이를 기반으로 구현하도록 역할을 분리해, AI가 임의로 데이터 구조를 변경하거나 요구사항을 추측해 설계를 확장하는 것을 제한했습니다.

  • 사람설계·판단·최종 승인
  • AI Agent설계 기반 구현·문서화
  • 검수 Agent코드·DB 호출·비용 검증
설계

1Jira 설계 문서 작성 형식 및 검수 기준 표준화

개발자마다 달랐던 설계 문서 작성 방식을 통일하기 위해 Jira 이슈에 기록할 설계 내용과 작성 형식을 직접 정의했습니다. 설계 문서에는 다음 내용을 공통으로 기록하도록 구성했습니다.

  • 데이터 구조 및 데이터 흐름
  • API 요청·응답 구조
  • 구현 내용 및 변경사항
  • 실제 실행 쿼리
  • 설계 판단 및 구현 이유 (AI가 개발자에게 질문해 답변 기반으로 작성)

AI가 구현한 후에도 동일한 형식으로 구현 내용을 Jira에 업데이트하도록 프로세스에 포함하고, 사전에 정의한 설계 문서와 실제 구현 결과를 비교하여 검수하도록 했습니다. 이를 통해 코드 전체를 다시 확인하기보다 표준화된 설계 문서를 기준으로 핵심 구현 결과와 설계 의도를 검증할 수 있도록 했습니다.

2Jira + Confluence + Atlassian MCP 기반 공통 기준 구축

개인별로 관리하던 개발 규칙과 문서 작성 방식을 팀 공통 기준으로 표준화했습니다.

  • Confluence · API 문서 형식 및 작성 예시 표준화
  • Jira · 기능별 설계 및 구현 내용 관리
  • Atlassian MCP · AI Agent가 Jira·Confluence의 설계 기준과 문서를 참조하고 동일한 형식으로 작업하도록 연동

이를 통해 개발 규칙과 설계 지식을 개인의 경험에 의존하지 않고, 사람과 AI가 함께 참조할 수 있는 기준으로 관리했습니다.

3비용 검수 Agent를 통한 이중 검증

기존에 발생했던 기능별 과도한 쿼리 호출 문제가 AI 구현 과정에서도 반복될 수 있어, DB 호출과 쿼리 비용을 별도의 검수 Agent가 확인하도록 구성했습니다. 최종 통합·튜닝 여부는 사람이 결정하도록 하여, AI의 구현 속도는 유지하면서 성능·비용을 별도로 검증하는 이중 방어 구조를 구축했습니다.

4Claude Code Skill(Dev-Flow)로 승인 절차 강제

Plan Mode로 요구사항과 설계를 협의한 뒤, 설계 승인 → AI 구현 → 설계 문서 업데이트 → Commit/Push 승인 → Build 승인 순서를 Claude Code Skill(Dev-Flow)로 고정했습니다. 개발자가 각 승인 단계를 직접 확인하기 전에는 AI가 다음 단계로 넘어가지 않도록 하여, 설계와 최종 실행에 대한 책임을 사람에게 두었습니다.

결과
  • AI를 단순 코드 생성 도구가 아닌 설계된 시스템을 구현하고 검증하는 협업 주체로 활용할 수 있는 개발 프로세스 구축
  • 2인 팀에서 약 6개월간 리뉴얼 기간에 개발한 모든 기능에 적용했고, 이후 신규 입사자가 합류해 3인 팀이 된 뒤에도 같은 프로세스로 작업
  • Dev-Flow 적용 후 유사 복잡도 기능의 후속 수정 이슈를 약 15건에서 7~8건 수준으로 감소 (AI 설계문서 Jira 이슈 기준)
  • 구현 후 AI가 구현 내용을 설계 문서에 업데이트하도록 하여, 담당자가 바뀌어도 설계 의도와 구현 근거를 추적할 수 있는 기반 구축
  • 기존 단일 기능 실행 시 최대 16개의 반복/개별 쿼리가 실행되던 문제를 비용 검수 Agent로 검수하고, 기능별 쿼리를 최대 5개 수준으로 제한하도록 구성
CASE 03

배달플랫폼 리뷰 AI 자동 답변 기능

LKF파트너스2026.07OpenAI GPT APINestJS · PostgreSQLDB 기반 Task Queue · Batch Scheduler
요구사항

기획팀 요청에 따라 배달플랫폼 리뷰에 대한 AI 자동 답변 생성 및 등록 기능을 개발했습니다.

  • 리뷰 내용을 기반으로 AI가 답변을 생성
  • 답변 스타일, 연령대, 답변 길이, 이모지 사용량을 선택할 수 있도록 구성
  • 선택한 조건을 조합하여 동일한 리뷰에도 다양한 답변을 생성
  • 생성된 답변 중 2개의 후보를 제공
  • 생성된 리뷰 답변을 설정된 시간에 자동으로 등록할 수 있도록 구성
판단
  • 리뷰 내용에 없는 정보를 AI가 임의로 생성하지 않도록 답변 생성 기준을 명확하게 정의해야 한다고 판단
  • 답변 스타일·연령대·길이·이모지 등의 조건을 독립적인 프롬프트로 구성하고 조합할 수 있도록 설계해야 한다고 판단

특정 리뷰 기능에 프롬프트를 종속시키지 않고 AI 타입·모델·시스템/유저 프롬프트를 공통 설정으로 관리하면, 향후 추가되는 AI 기능에서도 동일한 테이블을 활용할 수 있다고 판단했습니다.

설계

1모호한 리뷰에 대한 할루시네이션 방지

리뷰 내용에 없는 정보를 AI가 임의로 생성하는 것을 서비스 품질에 직접 영향을 줄 수 있는 가장 치명적인 상황으로 판단했습니다.

예를 들어 부정적인 리뷰에 단순히 감사 답변을 생성하거나, "신메뉴인가요?"라는 질문에 실제 확인되지 않은 사실을 답하거나, "ㅇㅇ ㄴㄴ"와 같은 의미 없는 입력에 대해 맛있게 드셨다는 식으로 리뷰에 없는 내용을 생성하는 경우가 있었습니다.

따라서 이러한 리뷰를 모호한 리뷰로 별도 분류하고, 공통적으로 사용할 수 있는 답변 규칙과 예시를 프롬프트에 정의하여 AI가 확인되지 않은 내용을 추측하지 않도록 설계했습니다.

2공통 프롬프트와 설정 영역 분리

시스템 프롬프트와 유저 프롬프트를 공통 템플릿으로 구성하고, 향후 설정되는 프롬프트는 유저 프롬프트의 특정 영역에 배치할 수 있도록 구조를 설계했습니다. 이를 통해 AI 기능별 설정이 달라지더라도 공통으로 유지해야 하는 프롬프트 규칙은 그대로 유지하고, 기능별 설정 부분만 변경할 수 있도록 구성했습니다.

테이블은 공통 AI 설정, 답변 스타일 프롬프트(공통), 유저별 설정으로 나누고, 유저별 설정에는 선택한 답변 스타일의 PK 목록만 저장했습니다. 답변 발송 시에는 공통 AI 설정과, 유저별 설정의 스타일 PK로 조회한 답변 스타일 프롬프트를 하나로 합쳐 프롬프트를 동적으로 생성한 뒤 API로 전송합니다.

3프롬프트 관리 구조의 공통화

AI 타입·모델·시스템 프롬프트·유저 프롬프트를 공통 구조로 관리하여, 향후 백오피스 관리자 페이지에서 기능별 AI 프롬프트를 목록화하고 조회·수정할 수 있는 구조로 확장할 수 있도록 설계했습니다.

4DB 기반 Queue와 스케줄러로 생성·등록 자동화

답변 생성 작업을 DB 기반 Queue 테이블에 적재하고 별도 워커 서버의 Node.js 스케줄러가 주기적으로 처리하도록 구성했습니다. 생성된 답변은 설정된 시간에 배달 플랫폼에 자동 등록됩니다.

작업마다 시작 시간, 처리 시간, 성공·실패 여부, 시도 횟수, 에러 코드와 에러 내용을 Queue 테이블과 로그에 함께 남기도록 구현하고, 최대 시도 횟수는 소스에서 설정하도록 했습니다. 최대 시도를 넘어 최종 실패한 작업은 마지막 에러 코드와 에러 메시지를 사람이 보고 판단해 수동으로 재실행하는 구조로 설계했습니다. 엘에스컴퍼니의 외부 주문 연동·장애 복구 설계에서 운영자용 재처리 화면(상품 연결 수정·개별 재처리)과 개발자용 일괄 재처리 API(전용 토큰 발급 → 검증 → 접근)로 운영하며 검증한 방식입니다 (CASE 05 역할별 복구 경로).

결과
  • 모호한 리뷰 분류와 공통 답변 규칙을 적용해, 검증 30건에서 리뷰에 없는 정보를 생성하는 할루시네이션 0건
  • AI 설정을 DB 공통 구조로 분리해 코드 배포 없이 모델·프롬프트를 변경할 수 있고, 다른 AI 기능에서도 같은 구조를 재사용 가능
  • 답변 조건 조합으로 동일한 리뷰에도 서로 다른 답변 후보 2개를 제공
  • DB 기반 Queue와 스케줄러로 답변 생성부터 예약 시간 자동 등록까지 자동화
CASE 04

정산 데이터 등록 자동화 관리자 기능 개발

LKF파트너스 · 사내 관리자 도구2026.01주 1회 · 정산 테이블 5종자발적 개선
문제

주간 정산 데이터 등록 업무를 맡으면서, 5개의 정산 기준별 데이터를 DB 관리 도구로 직접 테이블을 골라 등록해야 했습니다. 테이블을 잘못 고르거나 파일 구조가 맞지 않으면 오류가 날 수 있었고, 등록 후 문제가 생기면 해당 기간 데이터를 지운 뒤 다시 등록하는 방식으로 복구했습니다.

  • 정산 기준별 5개 테이블에 각각 데이터를 직접 등록하는 반복 업무
  • 파일과 테이블을 잘못 매칭할 경우 등록 오류 발생 가능
  • 컬럼명을 완전히 동일하게 비교하는 방식은 작은 차이에도 등록을 막아 사용자 부담 증가
  • 테이블별 데이터 타입만으로는 충분한 구분이 어려움
  • 주간 정산 기간이 휴일 등에 따라 달라질 수 있어 고정된 날짜 규칙만으로 처리하기 어려움
판단
  • 매주 반복되는 수동 DB 작업과 휴먼에러를 줄이려면, 개발자가 DB 도구로 하던 등록과 복구를 관리자 화면으로 옮겨야 한다고 판단
  • 검증은 등록을 최대한 막는 것이 아니라, 등록 가능한 범위에서 실제 오류만 DB 적재 전에 걸러내야 한다고 판단
  • 복구는 새로운 방식을 만들기보다, 기존에 하던 방식(그 주 전체 삭제 후 재등록)을 그대로 화면으로 옮기는 것이 가장 안전하다고 판단
설계

1등록 시점 3단 검증

파일명과 테이블명의 일치 여부를 기본 선택 규칙으로 사용하되, 파일명이 다르면 자동 선택하지 않고 사용자가 직접 테이블을 선택할 수 있도록 구성했습니다. 이후 테이블별 컬럼 수로 기본 구조를 검증하고, 각 셀의 빈 값 여부와 숫자형 컬럼의 숫자 입력 여부를 확인해 실제 오류는 DB 적재 전에 잡아냅니다.

2검증 기준을 고른 과정

  • 제외 · 컬럼명 완전 일치 비교 · 작은 차이에도 등록을 막아 사용자 부담이 커짐
  • 제외 · 데이터 타입 비교 · 테이블별 데이터 타입만으로는 충분히 구분되지 않음
  • 채택 · 테이블별 컬럼 수 · 테이블마다 컬럼 수가 달라 기본 구조 검증의 공통 기준으로 사용
  • 보완 · 셀 단위 검증 · 빈 값과 숫자형 컬럼의 숫자 입력 여부를 확인해, 등록 가능한 범위에서 오류를 사전 검출

3업로드 로그와 기간 단위 복구

업로드 로그 테이블을 별도로 두어 등록 이력을 확인할 수 있게 하고, 특정 정산 기간을 선택해 해당 기간의 데이터를 초기화한 뒤 다시 등록할 수 있는 복구 기능을 구현했습니다. 복구 후에는 재등록이 필요하다는 안내를 관리자 화면에서 제공합니다.

결과
  • 직접 등록과 테이블 확인에 약 20분 걸리던 작업을 약 1~5분으로 단축
  • 반복적인 DB 직접 작업을 관리자 화면으로 전환해 등록 과정의 휴먼에러 가능성 감소
  • 개발자가 하던 등록·복구 업무를 비개발자 담당자도 처리할 수 있도록 전환
  • 별도 요구사항 없이, 반복 수행하던 업무에서 비효율과 오류 가능성을 직접 발견해 설계·구현
CASE 05

티켓 주문/정산 시스템 리뉴얼

엘에스컴퍼니 · 관광 레저 플랫폼2020.01 – 2025.10PHP (CodeIgniter) · AngularJSMariaDB · MSSQL
문제

ASP/MSSQL 기반 레거시 티켓 시스템을 전면 재구축하면서 다음 문제를 해결해야 했습니다.

  • 외부 판매채널 주문 API를 서비스 서버에서 직접 처리해, 서비스 장애 시 외부 주문 수집까지 멈추고 해당 시간대 데이터가 누락될 가능성 존재
  • 장애 이후 외부 채널과 내부 주문 데이터가 어긋나면 개발자가 직접 확인·재처리해야 했고, 상품 연결 오류 같은 휴먼 에러도 개발자 개입이 필요
  • 판매채널 정산(결제금액)과 관광지 정산(입장·사용 횟수·회원 기준)의 기준이 다른데 하나의 상품 구조로 표현해, 상품 유형이 늘 때마다 테이블과 로직을 함께 수정
  • 어린이날·황금연휴 같은 피크 시즌에 주문이 몰리면 트랜잭션 대기와 DB Lock으로 커넥션이 늘어 서버 장애 발생
판단
  • 외부 판매채널과의 통신은 서비스 서버의 상태와 분리하고, 외부에서 받은 원천 데이터를 먼저 보존해야 한다고 판단
  • 모든 예외를 자동화하기보다, 운영자와 개발자가 각자 권한에 맞게 복구할 수 있는 경로까지 시스템에 포함해야 한다고 판단
  • 고객이 무엇을 얼마에 샀는지와 관광지에 얼마를 정산해야 하는지는 기준이 다르므로, 판매상품과 관광지 상품을 서로 다른 개념으로 분리해야 한다고 판단
  • 주문 후처리를 즉시 수행하지 않고 큐에 적재해 순차 처리하면 피크 시간대 부하를 분산할 수 있다고 판단
설계

1외부 채널·온라인 분리와 현장 시스템 연동

외부 판매채널과 온라인 서비스를 서버와 DB 단위로 분리했습니다. 현장 발권·R&B 재고 시스템은 당시 인력 부족으로 POS·키오스크를 수정 개발할 수 없어 별도 시스템으로 유지하고, 대신 POS·키오스크 API를 직접 개발해 현장에서도 온라인 티켓을 서비스 서버 API로 사용·취소할 수 있게 연결했습니다. 현장 관리 페이지의 온라인 정산은 현장 서버가 온라인 API를 호출해 보여주도록 구성했습니다.

2독립 API 서버와 원천 데이터 보존

기존에는 판매채널 주문 API를 서비스 서버가 직접 처리해, 서비스 장애 시 요청·응답이 유실되고 상품 연결 오류까지 모든 확인과 재처리를 개발자가 수작업으로 해야 했습니다.

외부 채널 연동을 독립 API 서버로 옮겨, 서비스 서버가 다운되어도 주문을 계속 받고 로그로 남기도록 했습니다. API 서버가 외부 채널의 요청·응답 원천 데이터와 처리 로그를 API DB에 먼저 보존하므로, 장애 시각을 기준으로 누락 여부를 확인할 수 있습니다.

3역할별 복구 경로

운영자는 재처리 화면에서 잘못 연결된 상품 수정, 주문 재처리, 불일치 데이터 보정을 직접 처리합니다. 원천 데이터는 서비스 서버가 아니라 API 서버에 있으므로, 운영자 화면이 내부 API로 API 서버를 호출해 처리합니다. 서비스 서버 장애처럼 개발자 개입이 필요한 경우에는 장애 시각을 기준으로 해당 구간을 일괄 재처리하는 개발자 전용 API를 두고, 개발자 전용 토큰 발급 → 검증 → 접근의 별도 인증을 적용했습니다. (위 After 그림의 아래쪽 두 경로)

4Queue 기반 비동기 처리

주문 후처리를 즉시 실행하지 않고 Queue 테이블에 적재한 뒤, API 서버의 스케줄러가 서비스 DB에 순차 반영합니다. 비용 문제로 스케줄러용 서버를 따로 두지 않고 API 서버에 함께 배치했습니다.

5판매·관광지 정산을 분리한 상품 데이터 모델

판매상품과 관광지 상품을 분리해 채널 정산과 관광지 정산을 독립적으로 계산하고, 판매금액·결제금액·정산금액을 단계별로 추적할 수 있게 해 재무팀이 직접 정합성을 확인할 수 있도록 했습니다. 상품 데이터 모델의 상세 구조는 CASE 07에서 다룹니다.

결과
  • 14개월간 설계·개발 후 현재까지 5년 이상 라이브 운영 중, 주문·티켓 사용 처리 일 수십만 건 규모
  • 실제 API 서버 장애 때도 서비스 서버는 정상 운영됐고, 반대 경우에는 API DB에 남은 큐 데이터로 복구 후 후처리를 이어가 장애 격리 효과를 운영 환경에서 확인
  • 피크 시즌 DB Lock 장애를 Queue 기반 비동기 처리로 해결
  • 상품 연결 오류·데이터 불일치는 비개발자가 직접 재처리하고, 장애 구간은 개발자가 일괄 복구하는 역할별 복구 체계 구축
  • 오픈 후 약 4년간 핵심 정산 구조 변경 없이 운영
  • 100만 건 이상 누적 데이터 조회 쿼리를 분석해 약 1분에서 10~20초 수준으로 개선
CASE 06

자사 공통 API 자동화 QA 프로세스 구축

엘에스컴퍼니 · 관광 레저 플랫폼2023.03자발적 개선PHP (CodeIgniter)QA 포털 · 체크리스트
문제

제휴처가 공통 규격에 맞춰 연동하는 자사 공통 API(채널용·관광지용)를 구축한 뒤에도, 신규 제휴처가 연동할 때마다 검증 과정의 반복 업무가 남아 있었습니다.

  • 신규 업체 연동 때마다 개발자가 정상·오류 요청을 직접 테스트해야 함
  • 별도 QA 인력이 없어 이메일로 5~8회 요청·응답을 주고받으며 최대 5일 이상 소요
판단
  • 반복되는 연동 검증은 개발자가 아니라 제휴처가 직접 수행할 수 있어야 한다고 판단해, 별도 요청 없이 QA 프로세스를 만들기로 결정
  • 채널용 API는 외부가 우리를 호출하고 관광지용 API는 우리가 외부를 호출하므로, 호출 방향에 따라 검증 방식도 달라야 한다고 판단
설계

1전체 구조 · 호출 방향에 따른 검증 방식

채널용 API는 판매채널이 우리 시스템을 호출하는 방향이라 제휴처가 QA 포털에서 직접 테스트할 수 있게 했습니다. 관광지용 API는 우리 시스템이 관광지 API를 호출하는 방향이라 QA 포털 방식이 맞지 않아, 공통 규격과 연동 조건을 기준으로 관광지 측이 직접 확인하는 체크리스트로 검증 절차를 구성했습니다.

2채널용 API Self-service QA 포털

  1. 1정상 주문
  2. 2취소·환불 시나리오
  3. 3오류·예외 상황
  4. ✓QA 완료 안내

실제 연동에서 반드시 확인해야 하는 시나리오를 단계로 정해 두고, 제휴처가 정해진 순서대로 직접 실행하도록 했습니다. 각 단계에서는 오류 상황도 의도적으로 발생시켜 응답과 대응 가이드를 함께 확인합니다. 모든 단계를 통과하면 "QA가 모두 완료되었습니다. 개발 완료 이메일을 보내주세요."라는 안내가 표시되고, 개발자는 통과 여부만 확인한 뒤 유관 부서에 연동 완료를 공유합니다.

결과
  • 이메일 5~8회 왕복, 최대 5일 걸리던 채널 연동 검증을, 제휴처가 QA 포털에서 결과를 실시간으로 확인하고 개발자는 단계별 테스트 통과 여부만 확인한 뒤 유관 부서에 연동 완료를 공유하는 방식으로 단축
  • 연동 방향에 맞춰 채널용은 QA 포털, 관광지용은 체크리스트로 검증 절차를 구분
  • 반복 테스트에 쓰이던 개발 리소스를 신규 연동과 시스템 개발에 집중
CASE 07

판매와 관광지 정산을 분리한 가변 상품 데이터 모델

엘에스컴퍼니 · 관광 레저 플랫폼상품 데이터 모델 재설계MariaDB
문제
  • 판매상품과 관광지 정산 기준을 하나의 상품 구조로 표현
  • 판매채널은 결제금액 기준, 관광지는 1회 입장·사용 횟수·회원 활성화 등 이용 기준으로 정산
  • 패키지(여러 관광지 중 일부 이용), 1회권·회차권·연간권마다 방식이 달라 유형 추가 시 테이블과 로직을 함께 수정
판단
  • "고객이 무엇을 얼마에 샀는가"와 "관광지에 얼마를 정산하는가"는 같은 기준으로 계산되지 않으므로, 같은 개념이 아니라고 판단
  • 상품 유형이 늘 때마다 테이블과 로직을 고치지 않도록, 이용 조건은 코드가 아닌 관계·조건 데이터로 표현해야 한다고 판단
설계

기존에는 하나의 상품에 판매가·채널 정산·관광지 정산 기준·이용 조건·패키지 구성이 모두 묶여 있어, 유형을 추가할 때마다 테이블과 로직을 함께 고쳐야 했습니다.

판매상품 → 상품연결 → 상품그룹 → 입장권의 4단계로 책임을 나눴습니다. 상품연결에서는 유효기간과 판매일·사용일 기준을, 상품그룹에서는 사용 가능 수량과 포인트 차감을 설정하고, 가격·채널은 판매상품에 1:N으로 연결했습니다.

판매가가 바뀌어도 관광지 정산 기준은 흔들리지 않고, 관광지의 이용·정산 기준이 바뀌어도 판매상품 구조는 그대로입니다. 새 상품 유형은 테이블 수정이 아니라 관계·조건 데이터 추가로 표현됩니다.

결과
  • 설계 결함으로 인한 치명적 정산 사고 0건
  • 오픈 후 약 4년간 핵심 정산 구조 변경 없이 운영, 현재 5년 이상 라이브 운영 중
  • 판매상품 → 상품연결 → 상품그룹 → 입장권의 4단계로 책임 분리
  • 하나의 판매상품을 여러 관광지 상품에 연결하는 패키지 표현
  • 유효기간, 사용 수량, 포인트 차감 등 조건을 코드가 아닌 데이터로 표현
  • 판매가격 변경과 정산 기준 변경의 상호 결합도 제거
CASE 08

티켓 주문/정산 시스템 및 POS/자사몰 개발·운영

브이패스2016.07 – 2020.01Delphi · JavaScriptPHP (CodeIgniter) · MySQL
A. 자사몰 상품 페이지 템플릿 구조
요구사항

디자인팀 요청으로, 자사몰 상품마다 상세 페이지를 따로 디자인하는 공수를 줄여야 했습니다.

  • 상품 관리자가 가격을 수정해도 디자인팀이 페이지를 다시 수정하지 않아도 될 것
  • 안내사항과 환불 규정 같은 내용도 디자인 작업 없이 반영될 것
판단
  • 상품 상세 페이지를 디자인이 필요한 영역과 데이터로 바뀌는 영역으로 나누면, 디자인은 한 번만 만들고 내용은 관리자가 설정으로 관리할 수 있다고 판단
설계

상품 상세 페이지를 메인 이미지, 가격 템플릿, 서브 이미지, 추가 안내사항, 환불 규정 등 주의사항의 다섯 영역으로 표준화했습니다. 가격은 템플릿으로 렌더링하고, 안내사항과 규정은 관리자가 설정만 해두면 자사몰에 자동으로 등록되도록 설계했습니다.

결과
  • 상품 관리자가 가격을 수정해도 디자인팀의 별도 수정 없이 자사몰에 바로 반영
  • 안내사항과 환불 규정도 설정만으로 자동 등록되어, 디자인팀은 이미지 제작에만 집중
  • 자사몰 상품 등록·노출 방식을 하나의 템플릿 구조로 표준화
B. Delphi POS IC칩 결제 전환
문제
  • 마그네틱 카드에서 IC칩 결제로 전환해야 했지만, 기존 Delphi POS와 신규 NICE IC 결제 모듈의 버전이 맞지 않아 직접 연동할 수 없었음
  • POS를 만든 전임 개발자는 퇴사한 상태였고, Delphi 경험이 없는 상태에서 POS와 결제 모듈 유지보수까지 맡아야 했음
판단
  • 기존 POS 프로그램을 크게 고치기보다, 버전 문제를 피해 결제 모듈을 연동할 수 있는 우회 경로를 찾아야 한다고 판단
  • Delphi가 웹 컴포넌트를 내장할 수 있다는 점을 활용해, 익숙한 웹 기술로 결제를 처리하는 것이 가장 안전하다고 판단
설계

1내장 웹 컴포넌트를 통한 결제 모듈 연동

기존 POS 프로그램과 결제 구조를 분석한 뒤, Delphi 내부에 웹 컴포넌트를 구성하고 JavaScript로 NICE IC 결제 모듈과 연동하는 중간 연동 구조를 구현했습니다.

2결제·DB 처리는 웹 레이어, POS에는 결과만 전달

결제와 DB 처리는 웹 레이어에서 수행하고 결과값만 POS로 전달해, 기존 POS 로직은 거의 수정하지 않도록 했습니다.

결과
  • Delphi 경험 없이 기존 구조를 분석해, POS 프로그램의 대규모 수정 없이 IC칩 결제 전환 완료
  • 버전이 맞지 않는 모듈을 직접 수정하지 않고, 웹 레이어를 중간 연동 계층으로 두는 방식으로 레거시 제약을 우회
마치며

“지금의 최선이, 앞으로도 최선일까?”

기능이 동작하는 것은 개발의 끝이지, 설계의 전부는 아니라고 생각합니다. 그 기능을 쓰는 사람, 운영하는 사람, 나중에 고칠 사람까지 떠올리며 구조를 정합니다.

지금의 요구와 비용에 맞는 수준을 고르되, 나중에 나눌 수 있는 경계는 미리 남겨 둡니다. 한 번 정한 구조도 운영하며 문제가 드러나면 다시 고민합니다.

AI도 같은 기준으로 씁니다. AI가 잘하는 일은 맡기고, 사람이 판단해야 할 지점은 더 분명하게 만듭니다. 자동화는 사람의 판단을 없애는 것이 아니라, 더 중요한 판단에 집중하게 만드는 일이라고 생각합니다.

설계할 때 늘 던지는 네 가지 질문
  1. EXTEND확장할 수 있는가지금 현실적인 규모로 개발하되, 추후 확장이 쉬운 구조를 선택합니다.
  2. USE사용하기 쉬운가실제로 쓰는 사람이 많이 실수하는 부분을 자동으로 검증합니다.
  3. TRACE추적할 수 있는가문제가 생겼을 때 원인을 찾을 수 있도록 데이터와 요청의 흐름을 남깁니다.
  4. RECOVER복구할 수 있는가문제가 발생했을 때 안전하게 복구할 수 있는 경로를 설계합니다.
